# ОкнаСтудия

Система класса «CAD + расчёт + производство» для оконно-дверного предприятия —
аналог IT Окна. Реализуется по плану `plan_analog_itokna.md`.

**Текущий этап: фронтенд MVP.** Работают журнал заказов, CAD-редактор изделия,
редактируемые справочники и живой расчёт: геометрия → стеклопакеты → фурнитура →
спецификация → цена. Расчёт пока выполняется в браузере, но написан как чистое ядро
без UI и хранилища, чтобы без переписывания переехать на сервер (план §3).

Структура справочников повторяет IT Окна: дерево профильных систем, а внутри системы —
вкладки **Общие · Параметры · Контура · Профили · Прилегания · Соединения · Заполнения ·
Фурнитура**, где у профиля и у заполнения есть собственная **Спецификация**
(Артикул, Цвет, Кол, Вид расчёта, Размер, Коэфф., Шаг, Размерность, **Параметры**, Тэг).

**Параметры и условия.** Параметры заводятся в справочнике «Параметры» (наименование,
уровень, скрытый, значение по умолчанию, список значений), задаются в конструкторе у
изделия или у створки, а строки спецификации и позиции комплектов фурнитуры отбираются
условиями вида `[Цвет ручки = Белый]` — так одна и та же комплектация даёт белую,
коричневую или серебристую ручку, а детский замок ставится только при `[Детский замок = да]`.

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # 16 тестов ядра расчёта
npm run build      # production-сборка
```

Данные заказов хранятся в localStorage браузера — это временная замена БД на время
фронтового этапа. Интерфейс store (`src/store/orders.ts`) намеренно повторяет
будущий REST API, так что подмена persistence не заденет компоненты.

## Архитектура

```
src/
  core/          ядро расчёта — чистые функции, ни UI, ни хранилища
    types.ts       доменная модель: справочники, входная модель изделия, расчётные структуры
    geometry.ts    геометрическое ядро: контуры, элементы, световой проём, СП
    spec.ts        «Вид расчёта» + фурнитура по фальцу
    pricing.ts     цены, наценка за цвет
    calc.ts        оркестратор: геометрия -> спецификация -> цена
    order.ts       свод по заказу
    scene.ts       иммутабельные операции над деревом деления
  catalog/       заводской срез справочников (VEKA Softline 70, REHAU Blitz 60)
  editor/        чертёж (SVG), панель параметров, панель спецификации
  settings/      редактируемые гриды справочника, вкладки системы, редактор спецификации
  pages/         журнал заказов, карточка заказа, редактор, справочники
  store/         заказы и справочники (localStorage; временно вместо API)
```

### Конвенции ядра

- Начало координат — левый нижний угол наружного габарита рамы, ось Y вверх,
  все размеры в миллиметрах. В SVG координаты переворачиваются на отрисовке.
- Световой проём контура = габарит минус ширина в плане профиля каждой стороны
  (стороны берутся из вкладки «Контура», поэтому порог или расширитель задаются данными).
- Створка садится на родительский профиль по «Прилеганию»: **dW/dH — суммарная добавка
  к ширине и высоте** относительно светового проёма родителя (двойной наплав).
- Заполнение = световой проём контура + dW/dH системного заполнения (двойной заход в фальц).
- Фальцевый размер створки (ФШ×ФВ) равен световому проёму родителя — это база подбора фурнитуры.
- Длина детали = габарит стороны + 2 × «Размер» углового соединения; импост — примыкание
  к телу: длина = проём + 2 × «Размер» соединения «Импост — Т».
- Положение импоста округляется до целого миллиметра.

> Семантику и знак dW/dH («суммарная добавка» против «добавки на сторону») нужно сверить
> с эталонным расчётом до запуска в производство — это риск из плана §10.

### Правило «никакого хардкода системы»

Ядро не содержит ни одной константы конкретной профильной системы: ширины в плане,
наплав, фальц, смещения соединений, состав фурнитуры и правила спецификации приходят
только из справочника. Вторая система (REHAU Blitz 60) держится в справочнике и
покрыта тестом именно как контроль этого правила (план §10).

> **Цифры справочника — стартовые.** Геометрия профилей подобрана под контрольный кейс
> плана, цены условны. Перед пилотом их обязан подтвердить технолог по узлам системы —
> для этого справочники правятся прямо в интерфейсе, без изменения кода.

Правки справочника сохраняются локально и сразу пересчитывают все изделия в заказах.
«Сбросить к заводским» возвращает файл `src/catalog/defaults.ts`; «Экспорт/Импорт JSON»
переносит настройки между машинами до появления серверного хранилища.

## Что дальше

1. **Печатные формы**: спецификация, бирки, заказ-наряд, договор.
2. **Обработки** (фрезеровки, сверловки) и проверка конфликтов на импосте — следующая
   вкладка системы после «Соединений». Туда же — «Элементы прилегания/соединения»
   (составы артикулов у самого узла), «Вставки», «Монтаж», «Комплекты».
3. **Сервер**: PostgreSQL + API; ядро расчёта переносится как есть (оно уже чистое),
   `input_model` изделия хранится JSONB — аналог `SCHEME2`.
4. **Импорт/экспорт `.itp`** и регрессия на реальных заказах (план §7, §9) — после
   выгрузки 30–50 эталонных заказов.
5. **Расширение геометрии**: штульп, порог и двери, несколько уровней импостов, арки и наклонные.
6. **Производство**: партии, сменные задания, раскрой 1D.
